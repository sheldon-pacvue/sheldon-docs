# Agent Hub 任务拆分 v2

> v1 → v2 主要变更：主线从"安装编排"转为"**目录 / 清理 / 启动门户**三位一体"。已实现的基础设施（CLI 骨架、错误码、JSON 信封、白名单、JSONL 日志、Adapter 接口、commander exitOverride、spawn/download 加固）**全部沿用**；本拆分只规划 v2 增量与重写部分。

## 1. 规划原则

- 技术基线：Node.js + TypeScript + commander（沿用 v1）
- 主线动作：`list` / `run` / `uninstall`
- 不重造轮子：运行时切换委托 mise/nvm/pyenv；包卸载委托原包管理器
- 交付节奏建议：10 周（增量分 5 个里程碑）

## 2. 关键路径

```
M0  v1 基线 (已完成)
 │
 ▼
M1  数据模型与 Adapter 重构      ← 必须先做，所有支柱依赖它
 │
 ├─►  M2  Inventory 引擎       ┐
 │         (list / inspect /   │
 │          adopt / scan)      │
 │                              ├─► M5  集成、测试、发布
 ├─►  M3  Cleanup 引擎          │
 │         (uninstall +         │
 │          dry-run / 快照)     │
 │                              │
 └─►  M4  Launcher 引擎         ┘
           (run + 运行时切换 +
            secret + 挂载)
```

M2 / M3 / M4 共用 M1 的成果后可**并行推进**。

## 3. 里程碑计划

### M0：v1 基线（已完成）

- CLI 工程骨架与 commander 命令树
- 错误码 `E_*` 与退出码 0/1/2/3/4/10
- JSON 信封 schemaVersion 1.0
- 白名单（URL + npm spec）
- 结构化 JSONL 日志、runId
- Adapter 接口 + OpenClaw / Hermes 内置实现
- scan 引擎 P0–P3 分级 + dry-run INSTALL_PLAN

**继承产物**：基础设施 100% 可复用；OpenClaw/Hermes 内置 adapter 转为 v2 adapter 内置集合的种子。

### M1：数据模型与 Adapter 重构（第 1–2 周）

#### Epic M1-E1：~/.agent-hub/ 目录骨架与 Run Context

**T1: 定义 Run Context schema 与读写**
- 输出：`src/runtime/run-context.ts`，含 zod 或手写 schema 校验
- 写：装/adopt 时落盘；改：`config <agent>` 命令；读：所有引擎共用
- 验收：能从 yaml 读出严格类型的 RunContext；非法 yaml 给具体行号错误

**T2: 数据目录初始化与迁移**
- 输出：`agent-hub` 首次运行自动建 `~/.agent-hub/` 子目录
- 含 `agents/` `adapters/` `snapshots/` `logs/`（已存在）`secrets/`
- 验收：目录权限 0700；secrets 子目录 0700

**T3: inventory.json 全局索引**
- 输出：`src/inventory/index.ts` 增量更新索引
- 验收：装/卸 / adopt / disown 后 inventory.json 立即一致

#### Epic M1-E2：声明式 Adapter

**T4: 声明式 Adapter schema 与 loader**
- 输出：`src/adapters/declarative.ts`，从 yaml 加载为 Adapter 接口实例
- 兼容内置 TypeScript Adapter（同一接口）
- 验收：写一份 cline.yaml 即可被 list/inspect 看见

**T5: Adapter Registry 与冲突仲裁**
- 输出：`src/adapters/registry.ts` v2
- 优先级：用户本地 > 远程缓存（V1）> 内置
- 验收：同 id 冲突时给清晰错误，不静默覆盖

**T6: 内置 Adapter 迁移**
- OpenClaw / Hermes 从 TypeScript 类 → 兼容层（同时支持 yaml 声明 + 必要时的 TS 钩子）
- 验收：v1 现有 install/dry-run 行为不回归

### M2：Inventory 引擎（第 3–4 周，可与 M3/M4 并行）

#### Epic M2-E1：可见性

**T1: 强信号读取**
- 直接从 `agents/*.yaml` 与 `inventory.json` 渲染
- 验收：管理过的 agent 100% 列出

**T2: 弱信号探测**
- 触发：`scan` 或显式 `list --detect`
- 来源：每个 adapter 的 `detect` + `typicalFootprint` + `npm/pip/brew` 原生命令
- 验收：受控样本池 ≥ 80% 准确率；不误报系统二进制

**T3: 健康度状态机**
- 状态：managed / detected / orphan
- 状态迁移规则：定义清晰，可被 inspect 解释
- 验收：每种状态都有自然的下一步建议

#### Epic M2-E2：信息呈现与操作

**T4: list 命令**
- 输出：表格形式（人类）/ JSON `data.agents[]`（机器）
- 选项：`--orphan` / `--unused` / `--by-source`
- 验收：80 列宽下不折行；JSON 字段稳定

**T5: inspect 命令**
- 单 agent 详情：source / footprint / runtime / env / 健康 / 占用空间
- 验收：包含 7 类信息，能定位任意疑问

**T6: adopt / disown**
- 把 detected → managed；不实际改文件，仅在 inventory 中记录
- 验收：adopt 后该 agent 可以 run / uninstall

### M3：Cleanup 引擎（第 3–5 周，可与 M2/M4 并行）

#### Epic M3-E1：安全卸载

**T1: 足迹合并与引用计数**
- 输出：`src/cleanup/refcount.ts`
- 算法：遍历所有被管 agent 的 footprint，构建路径 → 引用集合的反向索引
- 验收：refcount 算法单元测试 ≥ 6 case 覆盖（独占、共享、孤儿、shell-rc 段、嵌套路径等）

**T2: dry-run 计划生成器**
- 输出：每条 footprint 路径 + 引用计数 + 处理方式（删 / 跳过 / 警告）
- shell rc 改动以 unified diff 形式呈现
- 验收：所有 v2 的 uninstall 必须先经过 dry-run；非交互模式没传 `--yes` 时退 10

**T3: 委托式卸载实现**
- npm-global：调 `npm uninstall -g`
- pipx：调 `pipx uninstall`
- brew：调 `brew uninstall`
- curl-sh / manual：按 footprint 自行删除
- 验收：每种 via 单元测试 + 至少一种集成测试

**T4: shell rc 安全修改**
- 仅删 marker 之间内容
- 无 marker 不动；dry-run 中标记"以下行包含 agent 名但缺 marker"
- 验收：在含 marker / 无 marker / 跨 marker / 嵌套 marker 四种 fixture 上测过

#### Epic M3-E2：快照与回滚

**T5: 操作前快照**
- 改/删之前在 `snapshots/<runId>/` 落盘
- 含：被改 shell rc 全文、被删配置目录 tar.gz、操作前 inventory.json、操作清单
- 验收：每个 uninstall 都能在快照目录里"读到完整的 before 状态"

**T6: rollback 命令（V1）**
- MVP 不实现命令，但 M3 必须保证快照足以回滚
- 验收：手工回滚演练通过

### M4：Launcher 引擎（第 4–6 周，可与 M2/M3 并行）

#### Epic M4-E1：环境准备

**T1: 运行时切换探测器**
- 探测顺序：mise > nvm > fnm > volta > pyenv > 系统
- 给出"如何让运行时满足"的具体修复命令
- 验收：在不同 manager 装/未装的 5 种 fixture 机上行为正确

**T2: 运行时切换执行**
- 通过 manager 子命令切换（如 `mise exec node@20 --`）
- 不修改用户全局 shell 状态
- 验收：run 一个 Node20-only 的 agent，从 Node18 shell 启动也成功

**T3: Secret 解析器**
- 抽象 backend：env / file / keychain / 1password（MVP）
- URI scheme: `secret:<backend>:<key>`
- 验收：4 个 backend 各自单元测试覆盖；解析失败给精确错误

#### Epic M4-E2：启动与挂载

**T4: Skill / MCP 软链挂载**
- 装的时候记录挂载 marker
- 退出时清理 marker 软链
- 验收：异常退出时也能清理（SIGINT trap）

**T5: spawn + 信号陷阱 + 退出码透传**
- 输出：`src/launcher/spawn.ts`（与 exec/spawn.ts 区分；后者是子命令执行用）
- SIGINT/SIGTERM 透传给子 agent
- 子 agent 退出码 → agent-hub 退出码
- 验收：在交互式 agent 上 Ctrl+C 行为干净

**T6: run --shell**
- 不启动 agent，进 subshell 注入 env
- 提示符前缀 `[agent-hub: <name>]`
- 验收：在 zsh/bash/fish 三种 shell 上验证

**T7: 启动统计**
- runCount / lastRunAt 写入 inventory.json
- 验收：list --unused 能基于此过滤

#### Epic M4-E3：config 与诊断

**T8: config <agent> 编辑 + check**
- `config <agent>`：用 $EDITOR 打开 Run Context yaml
- `config <agent> --check`：校验运行时存在、secret 可解析、skill 路径存在
- 验收：check 失败给出具体修复命令

### M5：集成、测试、发布（第 9–10 周）

#### Epic M5-E1：跨平台与测试

**T1: 三平台冒烟矩阵**
- macOS / Ubuntu LTS：list / run / uninstall 全套
- Windows：list / inspect / uninstall（npm 部分）
- 验收：每平台至少 3 个 agent 跑通

**T2: 失败注入**
- 弱信号探测漏报、卸载共享资源、shell rc 无 marker、运行时缺失、secret 缺失、agent 启动崩溃
- 验收：每种失败给稳定错误码与下一步

**T3: 覆盖率提升**
- 关键模块（refcount, run-context, declarative-adapter, secret-resolver）≥ 80%
- 总覆盖 ≥ 75%

#### Epic M5-E2：发布与文档

**T4: v1 → v2 迁移工具**
- `agent-hub migrate-v1`：把 v1 安装路径转为 Run Context
- 验收：在 v1 装过 OpenClaw / Hermes 的机器上一键迁移

**T5: 文档与示例**
- 重写 README
- 出 `docs/run-context-schema.md` / `docs/adapter-schema.md`
- 至少 3 个 adapter yaml 示例（cline / aider / openclaw）

**T6: 发布流水线**
- CI 构建 → 测试 → changelog → npm 发布
- dist-tag 回退预案

## 5. 自检结论

- 所有 M1-M5 任务均有目标 / 输入输出 / 验收标准，可直接领取
- 与 v1 基线完全兼容：旧基础设施零回归

- 风险集中在 M3 的引用计数与 shell rc 修改、M4 的运行时切换跨平台——已在产品设计 §20 标注缓解策略

## 6. 0.0.1 发布计划（Mac dmg / GitHub Release）

0.0.1 的范围定义（与里程碑正交）：

1. **CLI 主线功能全部可用**（M4 收尾，含运行时切换 + secret + `run --shell` + `config`；Skill / MCP 挂载推迟到 0.0.2）
2. **Mac 桌面界面三屏可用**（list / inspect / uninstall 向导）
3. **GitHub Release 自动产出未签名 dmg**

技术选型：**Electron + electron-builder**，原因（节选）：
- 现有业务模块全是纯 ESM TS、无 native dep，Electron main 进程可直接 `import`，不必 spawn CLI、不维护两套类型
- 未签名 dmg 下"体积小"优势被吃掉，Tauri 的 Rust 桥变成纯成本
- `electron-builder` + GH Actions macos runner 的"未签名 dmg"模板成熟
- 后路开放：业务模块与壳解耦，0.1.0 想换 Tauri 只换壳

**关键工程决策记录**：

- *electron-builder 在 monorepo 下 hoist 重装 bug*：默认 `install-app-deps` 会在 appDir 跑 `npm install --production`，把 hoist 到根 `node_modules/` 的 devDeps（含 `app-builder-bin`）一起卸掉。修复：`electron-builder.yml` 设 `npmRebuild: false`，并把所有 desktop 运行时依赖（含 `@agent-hub/cli` workspace）移到 `devDependencies`——核心代码已经被 `electron-vite` 全量 bundle 到 `out/main/index.js`，runtime 不再需要 `node_modules`。
- *electron 版本探测*：monorepo hoist 后 `electron-builder` 无法从 appDir 推导，`electron-builder.yml` 显式声明 `electronVersion`。
- *npmjs.org 拉 Electron 二进制超慢*：国内开发期间用 `ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/` + `ELECTRON_BUILDER_BINARIES_MIRROR`；CI 在 GitHub macOS runner 上走默认源即可。
