# Agent Hub 产品设计 v2

> [!note] 知识库定位（相对本文档撰写时）
> 产品重心不仅是 Agent **安装/卸载**，而是交付**开箱即用的完整运行环境**（运行时、凭据、workspace、Skill/MCP 等），并通过 **CLI / 桌面等人机交互启动器** 便捷选用与切换。下文「目录 + 清理器 + 启动门户」中，**Launcher / 启动门户** 是用户价值的主轴；Inventory / Cleanup 为同一 Run Context 上的生命周期支撑。详见 [[agent-hub/产品定位]]。

> **v1 → v2 重大调整**：v1 把产品定位为"AI Agent 运行环境的扫描/安装/修复编排器"，主线是 `install` / `repair`。
> v2 重新把产品定位为 **AI Agent 工具的目录 + 清理器 + 启动门户（三位一体）**，主线动作变为 `list` / `run` / `uninstall`。
> 原因：在 AI Agent 工具爆炸式增长的当下，**安装本身已不再是难题**（任何 agent 一行 `curl|sh` 或 `npm i -g` 即可），真正稀缺的是：
> 1. 装了一大堆之后**说不清装了什么**；
> 2. 想卸又**怕误删共享依赖**；
> 3. 多个 agent **需要不同的运行环境**（Node 版本/Python 版本/API key/skill 集合），反复手动切换。
>
> v2 保留 v1 中已实现并仍然成立的基础设施：JSON 信封、错误码与退出码、白名单约束、`--output human|json`、结构化日志、`runId`、Adapter 接口骨架。被淘汰的是"以 install 为主线"的命令叙事、`repair --mode full/safe/incremental` 三档划分（safe/incremental 概念并入 inventory 一致性修复）。

---

## 1. 一句话定位

> **agent-hub 是 AI Agent 工具的「目录 + 清理器 + 启动门户」**——一处看到全部、一键切换启动、一次干净卸载。

更具象的开发者表述：

> `agent-hub run <agent>`——在正确的运行时版本、正确的 secret、正确的 skill 集合下启动它。装它、列它、卸它都从这里来。

## 2. 真正的痛点（v2 的判断）

针对**重度 AI 工具使用者**——一台机器上装过 5 个以上 agent 工具的开发者：

1. **可见性丢失**：`~/.local/bin`、`/usr/local/bin`、`~/`、`~/.config/`、`~/.cache/`、shell rc 各处散落几十个 agent 留下的痕迹；`brew list` / `npm ls -g` 看不全，更看不到 `curl | sh` 装的。
2. **不敢卸载**：一个 agent 占用 = 二进制 + 全局 node_modules + `~/.<name>/` + `~/.config/<name>/` + shell rc 改动 + 启动项 + ……。直接 `rm -rf` 可能误删共享依赖；不删又留着孤儿。
3. **环境切换摩擦**：每个 agent 期望不同 Node/Python 版本、不同 API key、不同 workspace、不同 skill/MCP 集合。切换一次要重置五件事，缺一就报错。
4. **新 agent 上手成本**：每周冒出新 agent，每个都要重新研究安装路径、配置位置、卸载方式。没有"标准入口"。

## 3. 三位一体的核心价值主张

| 支柱 | 回答的问题 | 关键命令 | 价值 |
|---|---|---|---|
| **Inventory（目录）** | "我装了什么？" | `list` / `inspect` / `adopt` | 把散落各处的足迹收编到一份可查的清单 |
| **Cleanup（清理器）** | "怎么干净卸载？" | `uninstall --dry-run` / `uninstall` | 引用计数 + diff 预览 + 快照 → 敢按卸载键 |
| **Launcher（启动门户）** | "在正确的环境下怎么启动？" | `run` / `run --shell` | 自动准备运行时 / secret / workspace / skill / mcp，再启动 |

三者共用同一份数据骨干——**Run Context**（§5）——所以是同一个产品。

## 4. 范围与边界

### 4.1 MVP（约 10 周）

- **Inventory**：list / inspect / adopt / scan（健康度）
- **Cleanup**：uninstall（含强制 dry-run、diff 预览、足迹快照）
- **Launcher**：run（运行时切换 + env 注入 + workspace + skill 软链 + spawn）
- **Adapter**：内置 `openclaw` / `hermes` / `cline` / `aider` 至少 2 个验证；同时支持本地声明式 yaml adapter
- **数据**：~/.agent-hub/ 目录骨架；JSONL 日志（已实现）；inventory.json
- **配置**：每个 agent 一份 `agents/<name>.yaml`（Run Context）
- **跨平台**：macOS / Linux 完整支持；Windows MVP 仅保证 list/inspect/uninstall 可用，run 的运行时切换在 V1

### 4.2 V1（MVP 之后）

- 远程 Adapter 仓库（社区共享 yaml）
- Windows 的 `run` 全功能（运行时切换走 mise/Volta/nvm-windows）
- 完整 Secret backend 矩阵（macOS Keychain + Win Credential + Linux Secret Service + 1Password CLI + .env）
- 可视化（doctor 的全屏 TUI 或 Web 控制台）
- 团队级 profile 模板与策略锁定

### 4.3 显式非目标

- **不替代** mise / nvm / pyenv / asdf 等运行时管理器——直接调用它们
- **不替代**包管理器——不自己下载二进制
- **不构建账号体系**，不托管云端凭据，不上报远程遥测
- **不自动 apply** 第三方 agent 平台的 skill / MCP 服务端配置
- **不做** GUI 桌面应用（V1+ 可考虑 TUI；GUI 留更远）

## 5. 核心数据模型：Run Context

Run Context 是 agent-hub 的**单一事实来源**。Inventory、Cleanup、Launcher 三件事都读它。

### 5.1 文件位置与结构

```
~/.agent-hub/
├── agents/                         每个 agent 一份 Run Context
│   ├── cline.yaml
│   ├── aider.yaml
│   └── openclaw.yaml
├── adapters/                       声明式 adapter（本地 + 远程缓存）
│   ├── builtin/                    内置（随版本发布）
│   │   ├── openclaw.yaml
│   │   └── hermes.yaml
│   └── user/                       用户/团队自定义
│       └── my-team.yaml
├── inventory.json                  足迹索引（被管 + 探测到的）
├── snapshots/                      卸载/修改前快照
│   └── <runId>/
├── logs/                           已有结构（JSONL）
│   └── <runId>.jsonl
├── state.json                      全局状态与版本
└── secrets/                        ★ 不储明文 secret，只放后端引用
```

### 5.2 Run Context Schema

```yaml
# ~/.agent-hub/agents/cline.yaml
schemaVersion: "1.0"
agent: cline
display: "Cline (Anthropic Code Agent)"

# --- inventory 侧：身份与足迹 ---
source:
  via: npm-global              # npm-global | curl-sh | brew | manual
  spec: "@anthropic-ai/cline"  # 跟 via 配套的标识
  installedAt: "2026-04-01T..."
  installedBy: agent-hub        # agent-hub | adopted | unknown

footprint:                      # 装的时候记账或 adopt 时探测
  binaries:
    - ~/.npm-global/bin/cline
  configs:
    - ~/.cline/
    - ~/.config/cline/
  caches:
    - ~/.cache/cline/
  shellRcEdits:                 # 必带 marker，否则不动
    - file: ~/.zshrc
      marker: "# managed by agent-hub: cline"
      lines: [47, 49]

# --- launcher 侧：怎么启动 ---
runtime:
  node: ">=20"                  # 由 mise/nvm 满足
  # 或 python: ">=3.11"
env:
  ANTHROPIC_API_KEY: "secret:keychain:anthropic-api-key"
  HTTP_PROXY: "env:HTTP_PROXY"  # 透传当前 shell 的 env
workspace: ~/projects/current
skills:
  - source: ~/.cursor/skills/cli-tui-design
    mount: ~/.cline/skills/cli-tui-design     # 软链入 cline 期望的位置
mcp:
  - filesystem
  - github
entry:                          # exec/spawn 谁、带什么参数
  command: cline
  args: []

# --- cleanup 侧：怎么卸载 ---
uninstall:
  via: npm-global               # 复用 source.via
  spec: "@anthropic-ai/cline"
  extraPaths: []                # 额外需要删除的孤立路径
```

**Inventory** 读 `source` + `footprint`；**Cleanup** 读 `footprint` + `uninstall`；**Launcher** 读 `runtime` + `env` + `workspace` + `skills` + `mcp` + `entry`。

## 6. Adapter 模型：声明式 + 内置混合

### 6.1 为什么改

v1 的 Adapter 是 TypeScript 类（`OpenClawAdapter`、`HermesAdapter`），每加一个 agent 都得改代码 + 发新版。在"每周冒出新 agent"的语境下太重。

### 6.2 新方案

```
内置 adapter（写死，质量高）  +  声明式 yaml adapter（无需发版，可社区共享）
        │                              │
        └──── 同一个 Adapter 接口 ─────┘
                  ▼
            Adapter Registry
                  ▼
            Run Context 渲染
```

### 6.3 声明式 Adapter Schema

```yaml
# ~/.agent-hub/adapters/user/aider.yaml
schemaVersion: "1.0"
id: aider
name: "Aider"
homepage: "https://aider.chat"

platforms: [darwin, linux, win32]

# 怎么"装"
install:
  primary:
    kind: pipx
    spec: aider-chat
  fallback:
    kind: pip-user
    spec: aider-chat

# 怎么"探测"是否已装
detect:
  command: aider
  args: ["--version"]

# 怎么"卸"
uninstall:
  kind: pipx
  spec: aider-chat

# 典型足迹（用于 adopt 与孤儿扫描）
typicalFootprint:
  binaries:
    - "~/.local/bin/aider"
  configs:
    - "~/.aider/"
    - "~/.config/aider/"
  caches:
    - "~/.cache/aider/"

# 启动需要的运行时
runtime:
  python: ">=3.11"

# 启动入口（用户可在 Run Context 中覆写）
entry:
  command: aider

# 期望的 skill 挂载目录（如果 agent 支持的话）
skillMount: "~/.aider/skills/"
mcpMount: "~/.aider/mcp.json"
```

### 6.4 Adapter 信任与白名单

- 内置 adapter：随 agent-hub 发布，签名/哈希内嵌
- 用户本地 adapter：放在 `~/.agent-hub/adapters/user/`，加载时仅校验 schema，不校验来源
- 远程 adapter（V1）：从受信仓库 URL（如 `github:agent-hub/registry`）拉取；首次加载需要 `agent-hub adapter add` 显式授权；继承 v1 的 URL 白名单机制

## 7. 命令模型

### 7.1 主线命令（用户高频接触）

```
agent-hub list [--orphan | --unused | --by-source]
agent-hub run <agent> [--shell] [--workspace <dir>] [--profile <name>]
agent-hub uninstall <agent> [--dry-run] [--purge]
```

`list` 与 `run` 是日常入口，`uninstall` 是低频但高价值动作。

### 7.2 完整命令树

```
=== 目录 / 状态 ===
agent-hub list                          列出所有 agent（管理的 + 探测到的）
agent-hub list --orphan                 只列孤儿（探测到但未管理）
agent-hub list --unused                 长时间未启动过的（基于 atime/启动日志）
agent-hub inspect <agent>               详细足迹 + Run Context + 健康
agent-hub scan                          整机健康检查（含每个 agent 配置可启动性）
agent-hub doctor [--collect]            诊断 + 可选打包

=== 安装 / 卸载 ===
agent-hub install <agent>               记账式安装（写入 Run Context 与 footprint）
agent-hub uninstall <agent>             安全卸载（必须走 dry-run）
agent-hub uninstall <agent> --dry-run   预览：会删什么、引用计数、diff
agent-hub uninstall <agent> --purge     连同 Run Context 一并清理
agent-hub adopt <agent>                 把探测到的孤儿纳入管理
agent-hub disown <agent>                反向：从管理中移除，但不卸载

=== 门户 / 启动器 ===
agent-hub run <agent>                   在配置好的环境中启动 agent
agent-hub run <agent> --shell           进入一个配好环境的 subshell，不直接启动 agent
agent-hub config <agent>                打开/编辑 Run Context yaml
agent-hub config <agent> --check        校验：运行时存在？secret 可解析？skill 在不在？

=== 扩展性 ===
agent-hub adapter list                  列已加载 adapter
agent-hub adapter add <url|file>        加新 adapter（声明式 yaml）
agent-hub adapter validate <id>         校验 adapter schema
agent-hub adapter info <id>             查看 adapter 详情

=== 其他 ===
agent-hub --help, --version             commander 标准
```

### 7.3 v1 命令的去留

| v1 命令 | v2 状态 | 说明 |
|---|---|---|
| `scan` | 保留并扩展 | 从"安装前体检"扩展为"整机 agent 工具健康度盘点" |
| `install <target>` | 保留但降级 | 不再是主线；语义是"记账式安装"——装完写入 inventory |
| `repair --mode safe/incremental` | **重新分类** | safe 概念并入 `inventory --fix`（修复孤儿、修复 PATH）；incremental 等价于 `uninstall && install` |
| `doctor` | 保留 | 诊断 + 可选诊断包 |
| `profile` | 重定义 | 从"环境基线模板"转为"我希望机器上有哪些 agent 工具的清单"（V1 才完整落地）|
| `mcp / skill <list|check|export>` | 保留 | MVP 仍仅检查/导出，apply 留 V1 |

## 8. Inventory 引擎

### 8.1 双信号源

| 信号 | 来源 | 准确度 |
|---|---|---|
| **强信号** | agent-hub 自己装的 → 直接读 Run Context | 100% |
| **弱信号** | 用户手动装的 → 主动探测 | 启发式 |

弱信号探测来源：

1. 已加载 adapter 的 `detect.command` 跑一遍（`cline --version`）
2. 已加载 adapter 的 `typicalFootprint` 路径存在性检查
3. `npm ls -g --depth=0` / `pip list --user` / `pipx list` / `brew list` 等包管理器原生命令
4. 扫 PATH 的所有目录，对 agent 已知二进制名做匹配

### 8.2 inventory.json 结构

```json
{
  "schemaVersion": "1.0",
  "generatedAt": "2026-05-11T...",
  "agents": [
    {
      "id": "cline",
      "status": "managed",                 
      "source": "agent-hub",
      "binaryPath": "~/.npm-global/bin/cline",
      "footprintSize": 482312345,
      "lastRunAt": "2026-05-10T...",
      "runCount": 17
    },
    {
      "id": "aider",
      "status": "detected",                
      "source": "unknown",
      "binaryPath": "~/.local/bin/aider",
      "footprintSize": null,
      "lastRunAt": null
    }
  ]
}
```

`status` 三态：`managed`（被 agent-hub 装/已 adopt）、`detected`（探测到但未管理）、`orphan`（足迹存在但二进制找不到）。

### 8.3 list 的两态视图

list 必须在视觉上**清晰区分"已管理"与"已探测"**——这是 inventory 引擎面对用户的承诺：
- 已管理：信息完整、可直接 run / uninstall
- 已探测：信息可能不完整，需要 `adopt` 后才能完整管理

## 9. Cleanup 引擎

### 9.1 三层防御机制

```
卸载前必经的三道关卡：

  [1] 足迹清单     ← 我打算删这些路径
       │
  [2] 引用计数     ← 这些路径里，有几个被其他 agent 引用？
       │           refcount > 1 的，不删，仅警告
       │
  [3] diff 预览    ← shell rc 改动用 diff 形式展示
       │           等用户输入 --yes 才执行
       │
       ▼
     快照 + 实际删除
```

### 9.2 引用计数

agent-hub 维护一个全局的"路径 → 引用它的 agent 集合"映射。卸载某个 agent 时：

- 该 agent 的足迹路径 `P` 引用计数 = 1 → 可删
- = 2+ → 仅从该 agent 的 footprint 中摘除，不实际删除文件
- = 0 → 异常（应在 inventory 阶段就修正）

### 9.3 共享资源策略

对于 npm 全局包，**不自己 `rm -rf`，必须委托原包管理器**（`npm uninstall -g`）。理由：
- npm 的全局 node_modules 可能被其他全局包共享
- 跨平台 PATH / shim 由 npm 维护
- 自己删容易留半残

同理 `pipx uninstall`、`brew uninstall`。

### 9.4 shell rc 安全修改

agent-hub 改 shell rc 时必须夹 marker 注释：

```bash
# >>> managed by agent-hub: cline >>>
export PATH="$HOME/.cline/bin:$PATH"
# <<< managed by agent-hub: cline <<<
```

卸载时**只在 marker 之间删除**；没有 marker 的行**坚决不动**，只在 dry-run 中显示"以下行包含 agent 名字符串但缺少 marker，需手动确认"。

### 9.5 快照与回滚

每次卸载前在 `~/.agent-hub/snapshots/<runId>/` 留：
- 被改的 shell rc 文件全文
- 被删的配置目录的 tar.gz 备份
- 操作前的 inventory.json
- 操作清单（precise）

提供 `agent-hub rollback <runId>`（V1）。

## 10. Launcher 引擎

### 10.1 执行流程

```
agent-hub run <agent>
│
├─[1] 加载 Run Context（找不到 → 报错并提示 inspect）
│
├─[2] 运行时切换
│       检测可用 runtime manager：mise / nvm / fnm / pyenv / volta
│       按优先级（mise > nvm > fnm > volta > pyenv）选第一个可用
│       计算需要的版本（Run Context.runtime 与已装版本比对）
│       不满足 → 输出 "运行 `mise install node@20` 后重试"
│
├─[3] Secret 解析
│       env 字段中的 `secret:<backend>:<key>` URI 解析
│       backend: keychain / wincred / 1password / file / env
│       解析失败 → 失败并指明缺哪个 secret
│
├─[4] Skill / MCP 挂载
│       用软链方式挂到 agent 期望位置
│       软链带 marker（agent-hub-managed 标记）
│
├─[5] cd 到 workspace（如果配置）
│
└─[6] spawn（不是 exec）
        派生子进程，继承新的 env，stdin/stdout/stderr 直通
        trap SIGINT/SIGTERM，传递给子进程
        子进程退出后：清理临时挂载，记录 runCount++ 与 lastRunAt
```

### 10.2 为什么 spawn 而不是 exec

- **临时挂载需要退出清理**（skill 软链、临时 MCP 配置文件）
- **统计需要进程后处理**（runCount、duration）
- **信号陷阱需要 agent-hub 在场**（Ctrl+C 时也要清理）

代价是多一层进程开销（约 50-100ms），但 agent 启动通常本身就 > 500ms，相对成本低。

### 10.3 退出码透传

子 agent 的退出码必须**精确透传**到 agent-hub 自身的退出码——上层 CI 脚本依赖它。

### 10.4 run --shell 模式

用户可能想要"环境配好但不启动 agent，进交互 shell 自己跑"。这个模式：

- 同样的 [1]-[5] 流程
- 第 [6] 步改为 spawn 用户当前 `$SHELL`，注入新 env
- 提示符前缀加 `[agent-hub: cline]` 让用户知道处在哪个 context

## 11. 横切关注点

### 11.1 运行时切换的具体策略

**优先委托现有工具**，不自己实现版本管理：

| Manager | 调用方式 | 平台 |
|---|---|---|
| mise | `mise exec node@20 --` | macOS / Linux / Win |
| nvm | `bash -c "source ~/.nvm/nvm.sh && nvm use 20 && exec ..."` | macOS / Linux |
| fnm | `fnm exec --using=20 ...` | 全平台 |
| pyenv | `pyenv shell 3.11` | macOS / Linux |
| Volta | `volta run --node 20 ...` | 全平台 |
| 系统自带 | 仅版本探测，不切换 | 全平台 |

**降级链**：mise > 用户当前激活的 nvm/fnm > pyenv > 系统版本（不匹配则失败）。

**Windows 注意**：MVP 不支持自动切换，run 命令仅校验当前版本是否满足，不满足直接失败。

### 11.2 Secret 管理

**核心原则**：不自己存明文，只存"如何取明文的引用"。

URI scheme：`secret:<backend>:<key>`

| backend | 解析 | 备注 |
|---|---|---|
| `env` | `process.env[key]` | 透传当前 shell |
| `file` | 读 `~/.agent-hub/secrets/<key>` 文件内容 | 权限 0600，agent-hub 自己不写入 |
| `keychain`（macOS）| `security find-generic-password -s <key> -w` | MVP 支持 |
| `1password` | `op read op://<vault>/<key>/password` | MVP 支持 |
| `wincred`（Windows）| Windows Credential Manager | V1 |
| `secret-service`（Linux）| `libsecret`-based | V1 |

**敏感值绝不出现在**：日志（JSONL）、stdout/stderr 截屏、错误 evidence、诊断包。

### 11.3 Skill / MCP 挂载

**MVP 用软链策略**：

```
Run Context 声明：
  skills:
    - source: ~/.cursor/skills/cli-tui-design
      mount: ~/.cline/skills/cli-tui-design

Launcher 执行时：
  ln -sfn ~/.cursor/skills/cli-tui-design ~/.cline/skills/cli-tui-design
  （目录下放一个 .agent-hub-managed 标记文件）

退出时：
  仅删除带 marker 的软链；其他不动
```

**用户场景**：
- 不同 agent 期望 skill 位置不同（Cursor / Claude / Cline）
- 用户希望同一份 skill 在不同 agent 间复用
- 退出时挂载点应当干净

### 11.4 跨平台

| 关注点 | macOS | Linux | Windows |
|---|---|---|---|
| shell rc 写入 | zsh/bash | bash/zsh/fish | PowerShell profile |
| 软链 | 原生支持 | 原生支持 | 需要管理员权限或 Developer Mode |
| Secret backend | Keychain | Secret Service (V1) | Credential Manager (V1) |
| 运行时切换 | mise/nvm | mise/nvm/asdf | mise/Volta（V1 才支持完整 run）|
| 路径分隔符 | `/` | `/` | 内部统一用 `/`，输出时按需转换 |
| 宽字符 | OK | OK | 用 width-aware 字符串长度 |

## 13. JSON 输出契约（保留 v1）

所有命令的 `--output json` 一律输出统一信封：

```json
{
  "schemaVersion": "1.0",
  "runId": "2026-05-11T...-abc123",
  "command": "list",
  "target": null,
  "ok": true,
  "changed": false,
  "issues": [],
  "nextActions": [],
  "logPath": "~/.agent-hub/logs/<runId>.jsonl",
  "data": {}             
}
```

v2 在 `data` 内放命令特定数据（如 `list` 的 inventory 数组），保持顶层信封字段稳定。

## 14. 交互原则

- **可预演**：所有写操作支持 `--dry-run`；`uninstall` **强制**走过一次 dry-run 才能执行
- **可恢复**：每个写操作前生成快照，提供 rollback（V1 完善）
- **可脚本化**：所有交互参数都有非交互映射；`NO_COLOR` / `CI` 环境变量受尊重
- **可追踪**：每次运行末尾打印 `runId` 与日志路径
- **默认安全**：高风险动作（uninstall, shell rc 改写）必须二次确认或 `--yes`

## 15. 安全模型

- 最小权限：默认不请求管理员；只在必要时引导用户单独提权
- 白名单：内置 adapter 受信；用户 adapter 仅校验 schema；远程 adapter URL 走 v1 已有的白名单 + hash 校验机制（V1）
- shell rc：只动自己 marker 之间的内容
- Secret：绝不出现在任何 agent-hub 自己写的文件中（日志、快照、诊断包）
- 诊断包：默认本地生成，导出前展示包含/排除清单，不自动上传

## 16. 失败恢复与回滚

- 幂等：`install` / `adopt` 重复执行不重复副作用
- 检查点：长流程（如 install）按阶段落盘
- 回滚（V1）：`agent-hub rollback <runId>` 基于 `~/.agent-hub/snapshots/<runId>/`
- 外部副作用：标记 `externalSideEffect: true`，不承诺回滚（如官方安装器对系统包的改动）

## 17. 日志与诊断

- 结构化 JSONL，按 `runId` 分桶（v1 已实现）
- 默认关闭遥测；本地诊断包按需 `doctor --collect` 导出
- 脱敏规则覆盖：`token / key / secret / password / authorization / Bearer / 私钥块 / 代理 URL 中的 userinfo`

## 18. 测试与验收

### 18.1 测试层级

- 单元：Adapter 接口契约、Run Context schema、足迹合并、引用计数算法
- 集成：list / inspect / install / uninstall / run 全流程，含失败注入
- 端到端：三平台冒烟（macOS / Ubuntu LTS 完整；Windows MVP 子集）

### 18.2 MVP 验收

- `list` 在装有 ≥ 3 个 agent 工具的开发机上能 100% 列出 agent-hub 管理的，弱信号探测准确率 ≥ 80%
- `uninstall --dry-run` 给出的"待删除路径清单"在受控样本池上人工核对 100% 正确（不误删、不漏删）
- `uninstall` 完成后，二进制不可用且 agent-hub 管理的足迹 0 残留；用户手动添加的同名目录保留
- `run` 在 5 个不同 Node 版本要求的 agent 间切换，每次启动延迟 < 3s（不含 agent 自身启动时间）
- `--output json` 通过 schema 校验，字段变更遵守兼容策略

## 20. 风险清单与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 弱信号探测准确率不达预期 | 用户失望，"看不见全部"| 渐进发布；对探测结果标记可信度；让 inspect 可手动修正 |
| shell rc 修改误伤 | 用户 shell 启动失败 | 严格 marker 机制；快照；提供 `agent-hub doctor --restore-shell` |
| 卸载误删共享资源 | 其他工具失效 | 引用计数；委托原包管理器；强制 dry-run |
| 多 runtime manager 共存的混乱 | run 切换失败 | 优先级清晰 + 失败时给出"装 mise 即可"的明确指引 |
| Secret 泄露 | 安全事件 | 不存明文；脱敏 + 单元测试覆盖 |
| 跨 agent 频繁切换的性能 | run 慢，用户回退手动 | 缓存运行时切换探测结果；spawn 时延优化 |
| Windows 体验滞后于 Mac/Linux | 用户流失 | MVP 明确"Windows 只支持 list/inspect/uninstall 子集"；V1 补齐 |

## 21. 自检结论

- 与 v1 已实现的基础设施完全兼容：JSON 信封、错误码、退出码、白名单、JSONL 日志、Adapter 接口骨架、`--output human/json`、commander exitOverride
- 主线动作从 `install` 转为 `list / run / uninstall`，对应用户的真实痛点
- MVP 范围克制：Inventory + Cleanup + Launcher 三大支柱，但每个支柱只做核心 80%；远程 adapter 仓库、Windows 完整 run、TUI/GUI 都后置
- 无外部依赖锁定：直接调用 mise/nvm/pipx/npm，可在任何阶段被替代
- 增长飞轮：`run` 高频带来 inventory 自然完整 → 完整的 inventory 让 uninstall 更敢用 → 用户越用越敢探索新 agent
